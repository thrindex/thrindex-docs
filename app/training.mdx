## Rate loss

The loss function is **rate loss**: the output LIF layer's spike counts over T timesteps are summed per output neuron, treated as a class score vector, and passed through cross-entropy.

```
score[c] = sum(output_spikes[:, c], axis=0)   # sum over T for each class c
loss = cross_entropy(score, true_label)
```

This formulation is principled for SNN classifiers: it rewards the network for making the correct class fire more than the others across the full temporal window, without requiring any particular timing. It is equivalent to the rate-coded cross-entropy used in Cramer et al. (2020) on SHD.

**Consequence:** if your output LIF neurons are largely silent (low firing rate), the class score vector is near-uniform and the model stays near chance. This is the most common failure mode in early training.

---

## Gradient clipping and surrogate gradients

Spiking networks are trained with **surrogate gradients**: the derivative of the spike function is approximated by a smooth surrogate (here, a fast sigmoid scaled by the surrogate slope parameter on each LIF layer). This makes backpropagation through the spike function well-defined but introduces gradient instability that is worse than in standard deep networks.

**Why clipping at 5.0 matters:** without clipping, gradients flowing back through long spike trains can explode, especially in the first few epochs when weights are random and firing rates are uncorrelated. The global norm clip at 5.0 prevents weight updates from destabilizing the network before it starts to learn.

You cannot change the clip value from the app. 5.0 is consistent with published SNN training practice on SHD-scale problems (Zenke and Neftci, 2021).

## Effect of T on training time

Training time scales linearly with T. Doubling T roughly doubles the time per epoch because every Dense and LIF operation runs over T timesteps.

| T | SHD bin size | Approximate time per epoch (Apple GPU, batch 32) |
|---|---|---|
| 25 | 56 ms | fastest |
| 100 | 14 ms | ~4x T=25 |
| 200 | 7 ms | ~8x T=25 |

For initial hyperparameter exploration, train for 5-10 epochs at T=100. Only scale T if the model is learning and you want to test whether finer temporal resolution improves classification.

## Learning rate selection

For SNN classifiers on SHD-scale datasets:

- `0.001` is a good starting point and works for most architectures
- If training accuracy oscillates or diverges after a few epochs, try `0.0003`
- If training is extremely slow to start (accuracy still near chance at epoch 10), try `0.003`

Lower learning rates are generally safer because surrogate gradient noise adds variance to the gradient estimate beyond what Adam's adaptive moment estimation can fully compensate for.

## Learning rate schedule

The **LR schedule** setting controls how the learning rate changes across epochs.

| Option | Behaviour |
|---|---|
| **None** (default) | Learning rate stays fixed at the value you set throughout all epochs. |
| **Cosine** | Learning rate follows a cosine curve from the initial value down to 0 at the final epoch. |

**When to use Cosine:** cosine annealing is the schedule reported in most SNN benchmark papers (Cramer et al., Zenke and Neftci). It tends to improve final held-out accuracy by 1-3 percentage points on SHD compared to a fixed rate, particularly when training for 30+ epochs. The benefit comes from the final phase of training where the lower learning rate allows fine-grained weight updates that a constant rate would overshoot.

<Tip>
If you are running a quick 10-epoch experiment, there is little benefit from cosine annealing - the curve has not had enough time to anneal. Use it for longer runs (30+ epochs) where the held-out plateau from a fixed rate is visible.
</Tip>

## Early stopping

The **Early stop** field accepts a positive integer - the patience. If held-out accuracy does not improve for that many consecutive epochs, training stops early and the model is sealed at the last epoch's weights.

Leave the field empty to run all planned epochs (default behaviour).

**How it works:**
- After each epoch, the held-out accuracy is compared to the best seen so far.
- If it improves, the patience counter resets to zero.
- If it does not improve, the counter increments.
- When the counter reaches the patience threshold, training stops.
- The model is always sealed, regardless of whether training stopped early.

**When to use it:** early stopping is most useful when you are not sure how many epochs you need and want to avoid overfitting on small custom datasets. For benchmark datasets like SHD, the held-out accuracy typically continues to improve slowly for many epochs, so a low patience (3-5) may stop too early.

<Note>
Early stopping has no effect if there is no held-out split. It is ignored for CIFAR10-DVS (which does not have a test set) and for custom datasets without test files or a validation split configured.
</Note>

The run manifest records the planned epoch count. You can tell a run stopped early by comparing the number of rows in `metrics.jsonl` with `project.train.epochs` in the manifest.

## Starting and stopping a run

Click **Train**. The first epoch may take longer than subsequent ones as the dataset loads into memory and the model is built on the device.

The status bar at the bottom of the window shows the current epoch, device, live loss, and training accuracy as each epoch completes.

To stop early: click **Cancel** in the status bar. A confirmation dialog asks before stopping. All completed epochs are preserved on disk and appear in the **Runs** view.

<Note>
Edits to the layer stack during training apply to the next run only. The running job uses the architecture it was started with.
</Note>

## Reading the metrics

### Loss curve

Loss should decrease monotonically in the first few epochs on a task the network can solve. Common patterns and their causes:

| Pattern | Likely cause |
|---|---|
| Flat from epoch 1 | Output LIF is silent (threshold too high relative to Dense output magnitude) |
| Decreasing then flat | Model is stuck in a local minimum; try a different seed or lower lr |
| Oscillating | Learning rate too high |
| Decreasing slowly and steadily | Normal. Continue training. |

### Accuracy - training vs held-out

**Training accuracy** measures how well the network classifies the training set. **Held-out accuracy** measures generalization to unseen recordings.

- Both stuck at chance (5% for 20 classes, 10% for 10 classes): the network is not learning at all. See the diagnostic section below.
- Training accuracy rises but held-out stays flat or diverges: overfitting. The network has memorized training recordings but not learned general features. Use fewer hidden neurons or more dropout (via code, not currently the app form).
- Both rise together: the network is learning. Continue training.

## Diagnosing a network that does not learn

If accuracy stays near chance for 5+ epochs, go through this checklist:

**1. Check T**
SHD recordings are 1.4 s. At T=11, each bin is 127 ms - most of the spike timing information is collapsed. Use T ≥ 100 for SHD.

**2. Check the output LIF threshold**
If the threshold is `1.0` and your Dense layer has a small number of output features (e.g. 20), the output LIF neurons may never reach the threshold. Lower the threshold to `0.3` or look at the spike raster after a few epochs to see if the output layer fires at all.

**3. Check the hidden LIF**
If the hidden LIF threshold is very low (< 0.1) or very high (> 2.0), either all neurons fire at every timestep or none fire. Both extremes kill learning.

**4. Check shape errors**
If the network diagram shows red connections, the architecture has shape mismatches. Training will fail with a worker error.

**5. Check the loss curve in the first epoch**
If the loss is not slightly lower at epoch 2 than epoch 1, nothing is being learned at all. This almost always means the output LIF is silent.

## Hardware and device

The Train view header shows which device is active:

- **Apple GPU** - Metal Performance Shaders (MPS). Used automatically on Apple Silicon when Compute is set to Auto.
- **CPU** - Used when no GPU is available, or when you have forced CPU-only in Compute settings.

<Tip>
Training on Apple GPU is typically 3-5x faster than CPU on Apple Silicon. Keep the Compute setting on Auto unless you are benchmarking CPU performance specifically.
</Tip>

For CPU thread and process priority settings, see [Compute](/app/compute).
